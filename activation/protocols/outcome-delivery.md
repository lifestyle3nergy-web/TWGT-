# TWGT Outcome Delivery Protocol

## Purpose
A repeatable static decision layer for moving from environmental demand to a measurable, authorised outcome.

## Flow
Environment → Demand → Observe → Understand → Outcome → Capability Map → Compose → Verify → Authorise → Publish → Measure → Evolve.

## Capability admission
A repository is evidence for a capability; it is not automatically the capability itself. Classify each candidate as:
- static-tool
- static-library
- static-skill
- runtime-service
- data-asset

For each candidate record source, license, owner, purpose, interfaces, dependencies, evidence, risk, provenance and status.

## Outcome rule
Do not start with a technology. Start with a demand and define the observable outcome.

## Composition rule
Prefer composition of proven capabilities over unnecessary new runtime surfaces.

## Evidence rule
READY requires evidence that the proposed composition satisfies the acceptance condition. Evidence must be traceable to a source.

## Human rule
AI may discover, analyse, draft and recommend. A human authorises admission, production action and customer-impacting decisions.

## Boundary rule
Static artefacts describe and coordinate work. Execution occurs only inside an approved runtime boundary.

## Failure states
BLOCK = unsafe, incomplete or contract-violating.
REVIEW = evidence or authority is incomplete.
ACTION = authorised next action is clear.
READY = acceptance evidence exists and human authorisation is recorded.
OPPORTUNITY = useful capability or demand identified but not yet committed.
